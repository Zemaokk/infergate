# M2.1 Per-key Token Bucket 行为合同草案

**状态：** 作者已完成基础预测并确认 key 输入规则；其余设计仍待定稿，尚未实现  
**分类：** A 类核心任务，作者先写第一版

## 目标与约束

为每个调用方设置独立的请求速率预算。每次被限流器允许的请求消耗一个令牌；
令牌随单调时间补充，最多达到桶容量。配置的容量和补充速率必须为正数。

作者于 2026-09-26 确认：使用 `X-InferGate-Key` header 作为配额标识；缺失或
空值直接拒绝，不创建 anonymous 桶。该标识不承担身份验证，不能把客户端自报
的值用于可信的多租户隔离。

输入错误沿用现有请求校验约定，返回 `400`，错误类型为
`invalid_request_error`、code 为 `invalid_infergate_key`、param 为
`X-InferGate-Key`。空字符串以及仅含空白的值都按空值处理。检查发生在创建或
更新 bucket、获取并发名额、选择及调用 backend 之前；拒绝不消耗令牌。

## 待作者确认的行为

| 项目 | 建议起点 | 需要明确的边界 |
| --- | --- | --- |
| 扣费单位 | 每个已通过验证的请求 1 个令牌 | 后续 backend 失败是否退还；建议不退还 |
| 初始状态 | 新 key 的桶从满容量开始 | 首次并发访问只能建一个桶 |
| 时间源 | 单调时钟 | 时钟差值取非负，避免倒退增加令牌 |
| 超额响应 | `429`，`rate_limit_exceeded` | 是否提供 `Retry-After` 及其取整方式 |
| 检查位置 | 请求验证后、选路和下游调用前 | 与全局并发容量的先后顺序 |
| 范围 | 单个 gateway 进程内 | key 数量增长的上界或清理策略 |

计算规则建议为 `tokens = min(capacity, tokens + max(0, now - last_refill) * rate)`。
当 `tokens >= 1` 才允许并扣除 1；否则拒绝。此处只定义目标行为，状态同步方式
和代码由作者先设计。

## 必须保持的不变量

1. 任何时刻 `0 <= tokens <= capacity`；同一 key 的并发请求不能同时花掉最后
   一个令牌。
2. 不同 key 的桶相互独立；拒绝的请求不消耗令牌，不触达 backend。
3. 取消和下游失败不得意外重复扣费；是否退费由合同明确，不能随异常路径变化。
4. 已有普通和 streaming 请求的透传、健康选路及资源关闭行为保持不变。

## 验证例子

- key 缺失、空字符串或仅含空白时返回 400，不创建 bucket、不调用 backend；
- 同一 key 依次消耗满桶、超额得到 429、时间前进后重新获准；
- 两个 key 的容量互不影响；
- 多个并发请求竞争最后一个令牌，只允许一个通过；
- 被拒绝请求的 backend 调用数为零；
- M1 streaming 与普通请求的现有测试仍通过。
