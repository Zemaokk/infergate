# InferGate 人机协作与学习契约

> 目标：在 1–2 周内交付一个可运行、可测试、可解释的项目，同时确保项目中的核心能力真正由作者掌握。

## 1. 两个同等重要的结果

本项目不只追求“代码能跑”，也不只追求“全部手写”。最终必须同时满足：

1. **Learning outcome**：作者能独立解释核心请求路径、共享状态、并发边界、失败行为和主要 trade-off。
2. **Delivery outcome**：仓库可安装、可运行、可测试、可 benchmark，并有足够清晰的文档供第三方复现。

如果二者冲突，先缩小功能范围，不通过牺牲理解来维持虚假的进度。

## 2. 比例如何计算

不按代码行数计算贡献比例，而按已完成的 **implementation tasks** 计算。一个 task 应是可以独立验收的工作单元，例如“实现 round-robin selector”或“配置 CI”。

整体目标：

- **核心机制：作者主导 70%，AI 主导不超过 30%**
- **工程配套：作者主导 30%，AI 主导可达到 70%**
- **设计决策和最终解释权：作者 100% 负责**

“主导”意味着先提出方案并完成第一版，而不是最终文件中谁输入了更多字符。AI 修改作者代码时，该 task 仍可算作者主导，前提是作者理解并接受修改。

## 3. 明确的代码边界

### A. 作者必须先写第一版

这些部分是项目最重要的学习内容。AI 先解释概念、帮助定义接口和测试，但默认不直接给出完整实现。

- round-robin routing
- backend state 与健康状态转换
- active request / pending load 的状态更新
- streaming 转发的核心控制流
- token bucket rate limiter
- concurrency limit 与 backpressure
- retry / fallback 的条件判断
- benchmark workload 与实验变量设计

作者写之前，需要能说清：输入、持有状态、输出、失败行为。

### B. 双方共同完成

这些内容既有学习价值，也容易包含陌生框架细节。作者先完成关键路径，AI 可以补全边界情况和重构。

- FastAPI endpoint 与数据模型
- async HTTP backend client
- timeout 与 cancellation propagation
- 单元测试和集成测试
- metrics 的定义与埋点位置
- configuration 与 dependency injection
- 模块拆分和 public interfaces

### C. AI 可以直接实现

这些任务以重复劳动、工具集成或表达质量为主，不应挤占核心学习时间。AI 实现后仍需说明改了什么以及如何验证。

- 项目脚手架和常规配置
- Dockerfile / Docker Compose
- CI workflow
- lint、format、type-check 配置
- Prometheus / OpenTelemetry 的样板接入
- Grafana dashboard 配置
- 测试 fixtures 与重复测试数据
- README、架构图、使用说明和发布检查
- benchmark 结果整理与绘图脚本

## 4. 默认工作流程

每个核心 task 按以下顺序完成：

1. **Contract**：先定义输入、状态、输出和失败行为。
2. **Prediction**：作者用自然语言或伪代码预测程序应该怎样运行。
3. **First attempt**：作者完成最小实现，不追求一次完美。
4. **Focused review**：AI 每次优先指出一个最关键、可验证的问题，而不是立刻重写全部代码。
5. **Verification**：共同补测试，并实际运行验证。
6. **Teach-back**：作者不用看答案，解释请求路径和至少一个失败场景。
7. **Record**：必要时更新设计文档或 decision log。

非核心 task 可以由 AI 直接实现，但仍必须经过 verification。

## 5. 卡住时的提示阶梯

核心任务卡住后，按以下级别逐步增加 AI 帮助，不直接从问题跳到完整答案：

1. 重新解释 invariant 或数据流
2. 给出一个定位问题的问题或小例子
3. 给出函数签名、测试用例或伪代码
4. 修改最小必要代码片段，并逐行解释原因
5. AI 接管该 task，作者随后通过 teach-back 和一次独立小改动完成理解闭环

默认在同一 task 上独立尝试 **30–60 分钟** 后升级帮助等级。环境、依赖和框架语法问题不需要硬撑，可以立即由 AI 协助。

## 6. 交付保护线

为了避免“为了学习一直做不完”，使用以下规则：

- 每个 milestone 必须先满足完成标准，再增加新功能。
- 单个非核心问题不得阻塞主线超过半天；超过后由 AI 直接处理或暂时降级。
- 核心 task 连续两次尝试仍无进展时，进入提示阶梯第 3 或第 4 级。
- 预计进度落后超过一个工作日时，优先删减 optional scope，而不是跳过测试。
- 接近交付窗口最后 25% 时进入 **delivery mode**：AI 可以直接完成未结束的集成、配置、测试和文档；核心算法仍需作者 teach-back。
- cache、Kubernetes、autoscaling 和复杂 token-aware scheduling 默认都是 optional，不阻塞第一版发布。

## 7. 阶段性比例

| 阶段 | 作者主导 | AI 主导 | 重点 |
| --- | ---: | ---: | --- |
| M0 最小闭环 | 70% | 30% | 理解 HTTP 转发、状态与路由 |
| M1 streaming / health | 60% | 40% | 理解 async、取消与失败处理 |
| M2 流量保护 | 70% | 30% | 理解并发、限流和 backpressure |
| M3 可观测性 | 40% | 60% | 正确定义指标，减少集成劳动 |
| M4 打包与 benchmark | 40% | 60% | 可复现交付和结果验证 |

这些比例是节奏控制目标，不是绩效数字。若实际偏离，在 milestone 复盘时说明原因即可。

## 8. “真正理解”的验收标准

一个核心 task 只有同时满足以下条件，才算完成：

- 作者能画出或口述数据流
- 作者能指出状态存放在哪里、何时变化
- 作者能解释至少一个失败场景
- 作者能预测一个新测试的结果
- 测试通过且不是只验证 happy path
- 作者能在不依赖 AI 的情况下完成一次小改动

不能复述每一行语法不算失败；无法解释状态和行为才说明尚未掌握。

## 9. AI 的行为约束

AI 在本项目中应当：

- 在动手前说明当前 task 属于 A、B 还是 C 类
- 核心 task 优先提问、解释和 review，不默认整段代写
- review 时指出具体 invariant、复现方式和影响
- 不静默扩大项目范围或更换关键技术方案
- 不用“看起来更生产级”代替可验证的工程理由
- 所有直接实现都运行相称的测试或检查
- 明确区分已验证事实、设计选择和待验证假设

### Git commit message 约定

- 每完成一个可独立提交的实现、测试、文档或验收任务，AI 在收尾回复中主动给出
  一条简洁的英文 Git commit message，放在代码块中，方便作者直接使用。
- 使用 `feat:`、`fix:`、`refactor:`、`test:`、`docs:` 等与改动相符的前缀；
  内容准确描述本轮实际完成的工作，不把计划中的功能写成已完成。
- 同一任务仍在逐轮 focused review 时，小修正不必每次单独提供；该任务收尾时
  给出覆盖整体改动的消息。作者明确索要时，立即提供。
- 消息应对应建议一起提交的改动范围；不默认包含工作区中其他未提交的修改。
- 提供 commit message 不等于执行 `git commit` 或 `git push`；提交与推送需有
  作者的明确指令。

## 10. 作者的行为约束

作者在本项目中应当：

- 核心 task 先写预测或伪代码，再写实现
- 不理解时直接指出具体断点，不假装理解
- 对 AI 提供的核心代码进行 teach-back
- 在增加功能前先让当前 milestone 可运行、可测试
- 保留失败实验和 benchmark 的真实结果，不只展示最好结果

## 11. 每个 milestone 的简短复盘

完成 milestone 后，在进度记录中回答：

1. 我现在能解释什么？
2. 哪些 task 由我主导，哪些由 AI 主导？
3. 哪个 bug 或失败让我学到了新的 invariant？
4. 哪些结果已经验证，哪些仍是假设？
5. 下一阶段是否需要调整范围或协作比例？
