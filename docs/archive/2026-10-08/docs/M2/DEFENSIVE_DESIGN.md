# M2.2 的防御性设计：保护什么，做到哪里

本文讨论当前 [app.py](../../../../../src/infergate/app.py) 与
[并发控制器](../../../../../src/infergate/concurrency_limiter.py) 的设计取舍。

## 1. 判断标准：失败后会破坏什么？

这里最重要的约束是：**每次成功获取名额，都有且只有一个责任方释放它。**

漏掉释放，会让网关逐渐失去可用容量；提前或重复释放，会让实际执行中的请求
超过上限。因此，失败路径上的资源清理属于功能正确性的一部分。

是否值得增加防御，可以问三个问题：

1. 能否指出具体的失败路径？
2. 不处理会破坏哪个约束，影响有多大？
3. 能否用一个小测试复现，新增代码是否与风险相称？

## 2. 为什么要包住整个 `__call__`？

endpoint 返回 `StreamingResponse` 对象后，框架才执行它的 `__call__`，发送
headers 并消费 body。名额必须覆盖这个阶段。

如果只在 body generator 的 `finally` 里清理，发送 headers 就失败时，generator
可能根本没有开始，清理也不会运行。当前包装的结构是：

```text
try:
    执行整个响应，包括 headers 和 body
finally:
    try:
        关闭下游 response
    finally:
        释放名额
```

外层 `finally` 覆盖响应执行失败，内层 `finally` 保证关闭抛异常时仍归还名额。
`finally` 本身不吞掉异常；但如果关闭也抛出新异常，新异常可能成为向外传播的
异常，原异常保留在异常上下文中。当前没有额外实现异常聚合或错误优先级策略。

## 3. `handed_off` 是明确责任，不是到处重复清理

| 阶段 | 清理责任方 |
| --- | --- |
| 获取名额后，选路或打开下游失败 | endpoint |
| 下游已打开，但响应对象构造失败 | endpoint 同时关闭下游并释放名额 |
| 流式响应对象构造成功并完成交接 | `LimitedStreamingResponse.__call__` |

交接标记必须在响应对象成功构造后设置。提前设置，构造失败时就没有责任方；
交接后 endpoint 仍释放，又会提前归还名额。

这是在正常 ASGI 响应执行流程中的所有权约定。标记本身不会自动强制“恰好一次”，
也不是应对进程被强制终止的保证。

## 4. 取消保护有范围，也有代价

关闭下游本身包含 `await`。外部 AnyIO 取消域已取消时，清理可能在等待点再次被
打断，所以当前只把 `aclose()` 放进 `CancelScope(shield=True)`。

这个保护用于完成清理，不包住整个推理任务。它保护的是 AnyIO 取消域语义，不能
据此声称能抵抗任意重复的 `asyncio.Task.cancel()` 或进程终止。

代价是：**当前清理没有独立的超时上限**。如果关闭一直不返回，名额仍会被占用。
现有测试验证了关闭成功、关闭抛异常和取消域中的关闭，没有证明任意情况下清理
都能及时完成。若后续观察到关闭卡住，再明确清理期限及超时后的资源处理策略。

## 5. 哪些“保护”可能掩盖问题或增加无效复杂度？

- **把计数夹在范围内不等于正确。** 当前 `release()` 使用 `min(limit, ...)`，
  能限制数值上界，却不能识别重复释放。例如上限 2、已占用 2，某个请求释放两次，
  `available` 会变成 2，而另一个请求仍在运行。正确性依赖责任交接与测试；测试中
  额外统计 `release()` 调用次数，避免只检查最终数值而漏掉重复释放。
- **内部配置不必每层重复校验。** key 来自外部，缺失或空白必须处理；`limit`、
  `capacity`、`rate` 当前由程序配置。将来开放配置入口时集中校验一次即可，
  无需为了重复检查打断核心流程的学习和验证。
- **当前不必为了计数增加锁。** 单事件循环下，同步检查与更新之间没有 `await`，
  其他请求协程不能从中插入。若改为跨线程共享，或在这段逻辑中加入等待，必须
  重新审视同步边界；多进程则需要另外的共享状态方案。
- **异常不能一概改成成功或重试。** 清理与错误恢复是两个决定。尤其响应已经
  提交后，不能通过返回新的 JSON 错误或透明重试来修补已经发送的流。

## 6. 当前证据与边界

[test_app.py](../../../../../tests/test_app.py) 覆盖发送 headers/body 失败、下游关闭异常、
取消、客户端断开、构造响应失败，以及正常和错误路径上的名额恢复。最近一次完整
测试为 **79 passed**，其中关键路径检查了释放次数。

这些证据来自受控 mock 和 ASGI 调用；不代表真实网络断开、生产负载或跨进程验证。
当前取舍是：为能够复现的资源生命周期缺口提供清理机制，并明确剩余假设；不把
参数检查、锁和兜底异常处理的数量当作稳健程度。
