# M4.4 Benchmark：设计合同

**2026-10-07：本地与真实模型实验均已完成工程验收，等待作者 teach-back 收尾。**

workload 与变量属于 A 类。本轮作者明确要求“你帮我设计合理的测试方案”，
因此由 AI 提供本版设计；作者保留设计决策和最终解释权。先本地受控实验，再
运行远程模型。实验工具独立于生产流控核心，真实测量复用已验收的推理环境。

## 目标与约束

分别回答网关开销、并发拒绝、per-key 限流和真实推理表现，不做全部变量的
全排列。首轮性能测量使用非流式请求。

- runtime 默认每 key capacity=2、refill rate=1/s，全局 concurrency limit=2。
- 当前普通 mock 无人工延迟，只有 Chat endpoint，不能稳定制造并发满额。
- key 扣额度先于全局并发检查：额度不足返回 429；额度充足但并发满额返回
  503/concurrency_limit_exceeded，且仍消耗本次 key 额度。
- `create_app` 可注入 limiter 实例。使用实验专用装配，不改变生产默认值；
  保留实际 HTTP client、健康检查生命周期、超时和观测配置。
- 远程环境需重新核对，不根据昨日 PID 或关机前记录断言当前服务状态。

## 第一组：成功请求的网关开销

问题：相同后端与负载下，经过网关的端到端成功延迟和成功吞吐如何变化？

| 项目 | 方案 |
| --- | --- |
| 后端 | 本地单个普通 Chat mock，无人工延迟 |
| 请求 | model=mock-model；单条 user 文本 `Briefly explain what an HTTP gateway does.`；stream=false |
| 对照 | 直连后端 / 经网关到同一个后端 |
| 负载 | 固定 worker 闭环，并发 1、2、4、8；每入口、每档 1,000 次请求尝试 |
| 额度 | 全局 32；一个固定合法 key，bucket capacity=100,000、refill=100,000/s |
| 预热 | 每入口、每档先发 50 次，全部完成后开始测量，预热排除出统计 |
| 重复 | 3 轮；每档依次使用 直连→网关、网关→直连、直连→网关 的顺序 |

客户端、网关和后端在同一台机器的独立进程，走真实 HTTP 与数值 loopback
地址；网关一个 worker。客户端复用连接，池容量至少覆盖并发 8，无客户端
重试。保留完成日志、metrics 和默认 trace 埋点，关闭 OTLP 导出。

闭环 worker 等前一个请求完成再发下一个；控制的是并发数，不是外部到达率。
这组提高额度以避免拒绝，测的是该实验配置，不代表默认容量 2 的表现。
预期没有 429/503；异常轮次保留并诊断，不删失败后冒充正常开销基线。
mock 结果不代表真实模型 token/s。

## 第二组：默认并发容量的拒绝与恢复

问题：容量为 2 时，真正重叠的请求如何接纳/拒绝，结束后是否恢复？

- 实验专用 mock 在普通响应前异步等待 200 ms，返回固定内容；不改变现有
  mock 默认行为。该延迟用于制造重叠，不模拟 GPU 计算性能。
- 全局容量 2；固定合法 key 使用第一组的大额度，排除 429。
- 每波同时释放 1、2、4、8 个请求，等全部响应结束才发下一波。
  每档 100 波，重复 3 轮；使用启动屏障并记录实际发送时间。
- 并发 1/2 预期全部成功；4/8 确实重叠时预期每波约 2 个成功，其余为
  503/concurrency_limit_exceeded。调度导致错开时，不能硬断言拒绝数量，
  应根据发送/完成时间判断负载是否有效。
- 拒绝日志 attempts=0、不应访问后端；普通成功为一次后端尝试。
  每档结束后确认 active=0，再发一个请求验证成功，检查容量释放。

有限波次避免“快速 503 → worker 立刻重发”产生大量拒绝而掩盖成功吞吐。
本组验证拒绝和恢复，不据此声称固定外部 RPS 下的极限容量。

## 第三组：per-key 限流

问题：固定 key 的两个初始额度与每秒一个补充额度如何影响接纳率？

- 单个零延迟 mock，全局容量 32；固定一个 key，默认 bucket capacity=2、rate=1/s。
- 分别按 0.5、1、2、5 请求/秒计划发送 30 秒，重复 3 轮。每 case 重建
  limiter，从满桶开始；按预定时刻发送，不等上一请求完成。
- 初始突发影响短窗口成功率，不硬写“2 请求/秒恰好 50% 成功”。根据实际
  发送时刻及 token bucket 规则核对，分别报告 200 与 429。
- 额外做一次双 key 隔离检查：两个固定 key 各按 2 请求/秒发送 30 秒，
  验证额度独立。不通过每请求换新 key 规避配额。
- 独立做顺序验收：全局容量改回 2、默认 key 配额；其他 key 的慢请求
  占满容量后，目标 key 连续请求应先得到并发 503，额度耗尽后得到 429。
  在一个 refill 周期内完成目标请求，并记录时序。该项不混入性能基线。

记录计划发送、实际发送及调度延迟。客户端跟不上时报告漏发并判该 case
无效，不能算成服务端拒绝，也不能悄悄延后补发。出现并发 503 时先诊断，
不能混作 key 限流。实验专用 limiter 包装记录实际判定时刻和剩余额度，
用于核对 refill 规则与 HTTP 结果；该包装仅用于额度/顺序验收，不加入开销基线。

## 第四组：远程真实模型对照

前置条件：前三组采集工具及结果校验通过。

优先复用已验收的 vLLM 0.10.1+cu118、Qwen2.5-7B-Instruct、单张 RTX4090。
启动后核对框架/依赖、GPU、模型版本、dtype、上下文上限、max_num_seqs、
GPU memory utilization、V0/V1、eager/graph、prefix caching 和生成配置，
将实际值写入 manifest。同一对照组保持配置一致，不混用旧 vLLM 0.8.5 数据。

| 项目 | 方案 |
| --- | --- |
| 位置 | 客户端、网关、模型服务都在租用机器，通过 loopback 测量；SSH 只负责控制 |
| 后端 | 单个真实服务；网关一个 worker，保留健康检查和默认观测埋点 |
| 协议 | Chat 非流式与 Responses 非流式分别测，不声称两协议计算量完全相同 |
| 正文 | 固定第一组的 user 文本；Chat max_tokens=64；Responses max_output_tokens=64、store=false |
| 生成条件 | 固定后端生成配置；Chat 可显式 temperature=0；Responses 不添加 schema 不支持的字段；记录实际配置 |
| 负载 | 并发 1、2；每个协议/入口/并发 50 次尝试，预热 5 次，重复 3 轮，交替直连/网关顺序 |
| 额度 | 全局 2；固定 key 使用大额度，先比较不超过容量的成功请求 |

客户端等待上限 120 秒；网关保持 runtime backend connect/pool=5 秒、
write/read=30 秒，区分客户端和网关后端超时。max tokens 是输出上限，
不保证实际 token 数相同；保存 usage 和输出长度。若启用 prefix caching，
明确报告为重复 prompt、预热后的工作负载，不推广到冷 prompt。

成功须 HTTP 200、协议结构有效且有非空文本；Responses 还需确认完成状态。
不重复 M4.2/M4.3 的停机/恢复验收。预计 GPU 测量约 10–30 分钟，不含环境
恢复及模型加载；这是计划估算，首个 case 完成后用实测速率修正。

## 统计与证据

每次尝试保存 JSONL：run/case/repetition/request ID、入口、key 别名、计划与
实际发送时间、完成时间、HTTP 状态、网关错误码、客户端异常、响应有效性、
usage（若有）。使用单调时钟计算耗时，绝不记录原始密钥。
另保存源码 commit/工作区状态、软件硬件环境、装配参数、正文、测量命令、
连接池/复用、日志/观测配置、mock 延迟、开始结束时间及完成日志。

- 成功率 = 有效成功数 / 全部已发出请求数。80 拒绝、20 成功时为 20%。
- 成功吞吐 = 有效成功数 / 测量时长。从首个测量请求发出到最后一个结束，
  排除预热。固定到达率另报 30 秒计划窗口与排空耗时，吞吐分母使用完整计划窗口加超出窗口的排空时间。
  未发出的计划请求单独列出，不算成功或拒绝。
- 成功延迟仅统计有效成功样本的 n、p50、p95；拒绝耗时另列。分别计数
  429、各原因 503、502、后端错误、无效 200 及客户端超时。
- 每轮单列，再汇总三轮中位值和范围，不只选最好结果。真实模型单轮 50
  样本的 p95 仅为探索性指标，不宣称稳定尾延迟或生产 SLA。
- 两组端到端 p95 的差不能当作每请求纯网关耗时；结合重复波动判断差异，
  波动无法区分时写“证据不足”，不强行声称性能变化。
- 完整响应耗时、网关 first-byte、模型 TTFT 不互相替代。非流式不报 TTFT；
  没有可靠 token 数和时间口径时不报 token/s。
- 功能要求拒绝原因正确、拒绝零次尝试、结束后容量恢复。性能暂不设置
  凭空的“开销必须小于 X ms”，不以快速拒绝降低整体均值作为性能提升。
